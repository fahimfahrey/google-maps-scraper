# Streamlit ↔ Playwright Real-Time Streaming Integration Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Wire `app.py`'s background `threading.Thread` to `scraper.py`'s Playwright engine through a `queue.Queue` so the Streamlit UI receives per-row data and live log messages in real time, while the Start Scraping button stays disabled for the duration of the run.

**Architecture:** A `queue.Queue` stored in `st.session_state.scrape_queue` acts as the one-directional pipe from the background thread to the Streamlit main thread. The scraper gains two optional callbacks (`row_callback`, `log_callback`) that the background thread binds to functions that save rows to the DB and put typed message dicts onto the queue. The `_status_panel` fragment (already auto-refreshing every 2 s via `run_every=2`) drains the queue on each tick via an extracted pure helper `_drain_queue(q, state)` and renders a live log expander using `st.empty()`.

**Tech Stack:** Python 3.14, Streamlit ≥ 1.35 (fragment `run_every`), `queue.Queue` (stdlib), `threading.Thread` (stdlib), `playwright.sync_api`, `pytest` + `unittest.mock`

**Skills to apply throughout:** `developing-with-streamlit` (session-state, fragment, st.empty patterns); `playwright-best-practices` (callback wiring); `pytest-coverage` (test structure)

## Architecture Decisions

### A. Callbacks in scraper, queue in app — not a queue in scraper

Passing a `queue.Queue` into `scraper.py` would import `queue` into the scraper and couple it to a transport mechanism. Instead `scraper.scrape_multi` receives lightweight `Callable[[dict], None]` callbacks; `app.py` binds those callbacks to closures that put typed dicts onto the queue. The scraper stays transport-agnostic and backward compatible (both new params default to `None`).

### B. Single `queue.Queue` with typed message dicts

Four message types carried on one queue:
```python
{"type": "row",   "data": adapted_dict}  # saved lead — increment counter
{"type": "log",   "text": "..."}         # progress text — append to log_lines
{"type": "error", "text": "..."}         # exception — set scrape_error
{"type": "done"}                          # run finished — clear queue ref
```

### C. `_drain_queue(q, state)` is a pure function accepting a plain `dict`-like object

Takes `out_q: queue.Queue` and `state: MutableMapping` instead of touching `st.session_state` directly. Called as `_drain_queue(out_q, st.session_state)` in the fragment. Pure dict in/out → unit-testable without Streamlit context.

### D. All queries passed to `scrape_multi` at once (not one-at-a-time)

Current `_run_scrape` calls `scraper.scrape_multi([query])` in a loop, so the inter-query delay inside `scrape_multi` never fires (single-element list = no delay). Fix: pass the full `queries` list to `scrape_multi` in a single call; the `log_callback` fires per query inside `scrape_multi` so the UI still shows which query is in progress.

### E. `db.save_lead` stays in the background thread

DB writes happen inside the `row_callback` closure that runs in the background thread. SQLite `check_same_thread` default is `False` in `database.py` (uses `with sqlite3.connect(...)`). This avoids bridging DB state across threads.

  ```python
  def _drain_queue(out_q: queue.Queue, state: dict) -> None:
      """Drain all available messages from out_q into state. Non-blocking.

      Message schema:
        {"type": "row",   "data": dict}   — increment leads_collected
        {"type": "log",   "text": str}    — append to log_lines
        {"type": "error", "text": str}    — set scrape_error
        {"type": "done"}                  — mark scraping finished, clear queue ref
      """
      try:
          while True:
              msg = out_q.get_nowait()
              mtype = msg.get("type")
              if mtype == "row":
                  state["leads_collected"] = state.get("leads_collected", 0) + 1
              elif mtype == "log":
                  logs: list = state.get("log_lines", [])
                  logs.append(msg["text"])
                  state["log_lines"] = logs
              elif mtype == "error":
                  state["scrape_error"] = msg["text"]
              elif mtype == "done":
                  state["scraping_active"] = False
                  state["scrape_queue"] = None
      except queue.Empty:
          pass
  ```

  > Note: `_drain_queue` does **not** call `db.save_lead` — row saving stays in `_run_scrape`'s `on_row` closure (background thread). The "row" message is only a signal to increment the counter.

## State Management Strategy

| Key | Type | Initial | Set by | Consumed by |
|-----|------|---------|--------|-------------|
| `scraping_active` | `bool` | `False` | button handler (→`True`); `_drain_queue` on `done` (→`False`) | button `disabled`; `run_every`; status metric |
| `leads_collected` | `int` | `0` | button handler resets; `_drain_queue` increments on `row` | status metric |
| `current_query` | `str` | `"—"` | `on_log` closure in `_run_scrape`; `finally` resets | status caption |
| `scrape_error` | `str\|None` | `None` | button handler clears; `_drain_queue` on `error` | `st.error()` |
| `scrape_queue` | `queue.Queue\|None` | `None` | button handler creates; `_drain_queue` on `done` clears | `_status_panel` drain |
| `log_lines` | `list[str]` | `[]` | button handler resets; `_drain_queue` appends on `log` | live log expander |

**Thread-safety note:** `st.session_state` writes from the background thread (`on_log` closure writing `current_query`, `finally` writing `scraping_active`/`current_query`) are safe in Streamlit ≥ 1.11 which uses a per-session lock. The queue itself is stdlib `queue.Queue` which is thread-safe by design. All other session-state mutations happen in the main thread via `_drain_queue`.

## Risks and Edge Cases

| Risk | Mitigation |
|------|-----------|
| **Browser process leaked on `st.rerun()`** | `t.start()` runs in `finally`-safe thread; `daemon=True` means process dies if parent dies. `scraping_active` guard prevents double-click spawning. |
| **Fragment still polling after done** | `_drain_queue` sets `scraping_active=False` on `done` → next script rerun sets `run_every=None` → fragment stops. One extra 2 s tick may occur; harmless. |
| **`on_log` closure captures `out_q` by reference** | `out_q` is created fresh per button click and stored in `scrape_queue`; no stale reference risk. |
| **Old `scrape_queue` from previous run persists** | Button handler always resets `st.session_state.scrape_queue = out_q` (new queue) and `log_lines = []` before starting thread. |
| **`queue.Queue` in session state serialisation** | Streamlit session state stores Python objects in memory (not serialised). `queue.Queue` is safe. |
| **`_drain_queue` called when `scrape_queue` is `None`** | Fragment checks `if out_q is not None` before calling `_drain_queue`. |
| **Playwright `sync_playwright` blocks GIL** | Playwright's sync API releases the GIL during I/O waits. The 2 s fragment refresh is unaffected; Streamlit's ASGI server handles main-thread work independently. |
| **Error mid-query leaves partial data** | `finally` always puts `{"type": "done"}` → UI unlocks. DB rows saved before the exception remain. User sees error in `st.error`. |
| **`leads_collected` out of sync with DB** | Counter is driven by `"row"` messages (one per saved lead). DB count shown via `database.count_leads()` called fresh in the fragment. Both reset on new run. |
